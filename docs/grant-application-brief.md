## 一、执行摘要（顾问最先看的半页）

爱尔兰大量中小餐饮商户仍依赖 **电话外卖、纸质记忆、旧 POS 或零散 Excel** 管理客户与订单，换系统时怕 **丢失客户地址**、怕 **重买设备**，也难以从复购数据里做 **有效推荐**。

**LZFood** 是 **B2B 多租户** 云端平台：一家科技公司服务 **许多** 餐馆/咖啡店/外卖店，提供 **扫码点餐、收银 EPOS、送餐与电话单、会员储值、营业报表** 等；商户用 **现有平板/电脑浏览器** 即可开工，并可将 **旧系统客户资料迁入**，后续通过 **菜品标签、订单历史与 AR 菜单** 提升点单效率与客单价。

**申请方向建议**：  
- **Feasibility Grant** — 验证「客户迁移 + 设备兼容 + 标签化订单智能 + AR」在爱尔兰市场的商业与技术可行性；  
- **Priming Grant**（在 Feasibility 之后）— 区内试点推广、招聘实施与销售、本地化营销。

**English summary (for forms)**  
LZFood is an export-oriented, multi-tenant B2B SaaS platform for hospitality EPOS, ordering and operations. It lowers adoption risk through legacy customer-data migration and reuse of existing devices, and differentiates through tag-based order intelligence, explainable recommendations, and AR menu discovery for Irish and international SMEs.

## 二、项目性质（避免被误解为「开餐馆」）

| 项目 | 说明 |
|------|------|
| **我们是什么** | 向餐饮商户 **销售/订阅软件服务** 的科技公司（SaaS） |
| **我们不是** | 餐饮门店经营者；单店展示型网站制作 |
| **交付形态** | 同一网站多店铺路径，如 `/{店名}/customer`（顾客）、`/{店名}/cashier`（收银）、`/{店名}/admin`（管理） |
| **收入模式** | 门店订阅与功能套餐；各店 **独立 Stripe** 收款；平台级门店自助注册（门户） |
| **数据隔离** | 每店数据独立，符合多商户 SaaS 合规预期 |

## 三、商户痛点（申请书写「市场问题」）

1. **电话/外卖占比高**：地址、Eircode、运费易错，新人上手慢。  
2. **老客靠人记**：常点菜、口味偏好无系统记录，忙时漏推荐。  
3. **换系统成本高**：怕丢客户名单；怕再买一套硬件。  
4. **线上线下割裂**：扫码、吧台、送餐、储值若多套系统，对账难。  
5. **竞争与毛利压力**：需要 **提效（少出错、少培训）** 与 **复购（推荐、储值）**，而非仅「有个二维码菜单」。

## 四、目前已有产品与功能（事实基础 · 证明项目已启动）

以下能力 **已在产品中存在或已具备运营路径**，表明课题是在 **成熟 MVP 上** 做创新与商业化，而非纸上谈兵。

### 4.1 点餐与订单（全渠道）

| 能力 | 商户得到什么 |
|------|----------------|
| **堂食扫码** | 桌码/座码点餐；支持 **先付** 与 **后付** 两种堂食流程 |
| **自取 Takeaway** | 每日序号、时段展示；收银或顾客端下单 |
| **电话单 Phone** | 符合爱尔兰手机号规范；支持 **下单时已刷卡** 等电话收款场景 |
| **送餐 Delivery** | 地址、**Eircode 自动补全**、**配送距离与运费规则**、配送阶段跟踪 |
| **实时订单** | 收银端订单刷新（WebSocket），减少漏单、重复问厨房 |

### 4.2 收银与结账（EPOS 核心）

| 能力 | 商户得到什么 |
|------|----------------|
| **统一结账** | 现金、刷卡、混合支付；与优惠券、套餐优惠联动 |
| **按桌/按座结账** | 堂食后结场景下灵活结账 |
| **订单改单** | 结账流程中调整菜品，减少重新开单 |
| **小票打印** | 浏览器打印（无需先换专用云打印机即可营业） |
| **订单中心** | 统一查看活跃订单，适配先付/后付不同状态 |

### 4.3 会员与储值（提高复购与现金流）

| 能力 | 商户得到什么 |
|------|----------------|
| **会员账户** | 手机号会员、PIN、余额与 **完整流水** |
| **吧台/扫码会员付** | 余额充足时快速结账；规则清晰防对账混乱 |
| **Stripe 自助充值** | 顾客在线给账户充值 |
| **实体储值卡** | 批次制卡、激活、核销，适合礼品与促销 |
| **后台充值** | 按金额或 **「充值至目标余额」**（便于月度固定额度客户） |

### 4.4 客户档案（送餐/电话场景）

| 能力 | 商户得到什么 |
|------|----------------|
| **CustomerProfile** | 按电话保存多套地址与邮编；选客人即带出信息 |
| **常点菜品** | 根据历史订单统计 **本店常客爱吃项**，收银送餐时一键参考 |
| **与会员并存** | 送餐档案与会员钱包可协同（同一电话逐步统一体验） |

### 4.5 门店后台（日常运营）

| 能力 | 商户得到什么 |
|------|----------------|
| **菜单与分类** | 多语言、图片、选项组模板、过敏原 |
| **AR 菜单** | 菜品 **3D/AR（USDZ）** 展示，顾客扫码可「先看再吃」，提升决策与客单价潜力 |
| **库存/售罄** | 即时停售，减少下单后无法出餐 |
| **套餐 Offers / 优惠券 Coupons** | 促销规则化，减少人工算价错误 |
| **营业报表与 VAT 相关导出** | 支撑日常对账与会计沟通 |
| **配送费、营业时间、QR 码** | 一店一配，无需改代码 |
| **每店 Stripe** | 线上下单收入进商户自己的 Stripe |

### 4.6 平台与多店 SaaS

| 能力 | 商户得到什么 |
|------|----------------|
| **多店隔离** | 一套系统服务多个品牌/门店，利于 LZFood 作为 **软件公司** 规模化 |
| **功能套餐** | 按店开通送餐、会员等模块，匹配不同规模商户 |
| **门户注册** | 新商户在线申请开店、验证邮箱（降低销售成本） |
| **平台管理员** | 订阅期、续费、跨店支持（含审计方向） |

### 4.7 已有「过渡性」能力（可写进「降低换系统风险」）

| 能力 | 商户 / 资助叙事价值 |
|------|---------------------|
| **客户 CSV 导入路径** | 可将旧系统/Excel **客户名单与地址** 迁入，避免从零录入（产品化向导为规划项） |

## 五、规划开发的功能（申请书中写「创新与下一阶段」）

> 下列为 **产品路线图**，用于 Feasibility 研究内容或 Priming 商业化范围；**不是**声称已全部完成。

### 5.1 商户最易感知（建议 Feasibility 主叙事）

| 功能 | 做什么 | 商户价值 |
|------|--------|----------|
| **旧系统客户与订单同步（产品化）** | 向导式导入 CSV/旧 POS 导出；增量更新；标记数据来源 | **换系统不丢老客**；开业首日即可电话送餐；为推荐提供历史 |
| **菜品 Tags + 订单智能** | 每道菜多标签（口味、素食、招牌等）；按客人历史做 **共现与偏好**；收银侧 **可解释推荐** | 忙时少问「还是老样子吗」；提高 **加菜与客单价**；新员工培训更快 |
| **送餐/电话历史增强** | 按时间查历史单、「再来一单」、与推荐联动 | 减少重复输入；缩短每笔送餐单耗时 |
| **现有设备深度兼容** | 研究并试点 **热敏小票机（ESC/POS）**、**来电显示与收银联动（CTI）** | **不用扔打印机、不用换电话系统** 也能升级数字化 |
| **AR + 推荐联动** | 推荐区标注「可看 AR」；标签筛选与招牌菜曝光 | 差异化体验，吸引年轻客群与游客 |

### 5.2 运营与规模化（Priming 或第二期）

| 功能 | 做什么 | 商户价值 |
|------|--------|----------|
| **断网收银与自动同步** | 断网本地暂存订单；恢复后 **幂等上传** | 农村/地下室信号差时 **不停业** |
| **高并发与高峰** | 节假日扫码与多收银台并发优化 | 圣诞、赛事日不宕机、不丢单 |
| **全渠道退款编排** | Stripe/现金/会员钱包退款 **自动联动** 订单行与报表 | 少人工对账、少会计纠纷 |
| **连锁总部视图** | 多店报表、统一菜单策略（若市场需求确认） | 小连锁扩张时管理成本可控 |

### 5.3 路线图时间表述（给评审看节奏）

- **0–9 个月（Feasibility）**：市场与竞品、迁移样本、Tags/推荐访谈、设备集成可行性、AR 与推荐商业小结 → **报告 + 更新商业计划**  
- **9–24 个月（Priming + 自营研发）**：试点店 onboarding、标签体系上线、推荐 MVP、雇实施/销售、区内推广

## 六、对商户的整体价值（可原样写入「Benefits」）

1. **少出错、省时间**：地址邮编、运费、常点菜、推荐减少重复劳动。  
2. **多赚钱、促复购**：储值锁客、优惠券/套餐、AR 与推荐提升客单。  
3. **换系统更敢换**：旧客户导入、旧设备继续用，降低一次性投入与心理门槛。  
4. **一套系统管多渠道**：堂食、自取、电话、送餐、会员、报表同一后台。  
5. **符合爱尔兰习惯**：Eircode、手机号、Stripe、英文/中文界面。  
6. **可成长**：从单店到多店套餐，软件公司持续更新，商户不绑死在单店网页。

## 八、与 LEO 补助的对应关系（提高成功率怎么写）

### 8.1 Feasibility Study Grant（建议先申）

**课题标题（英文）**  
*Feasibility Study: B2B Hospitality EPOS SaaS — Legacy Customer Migration, Device Interoperability, and Tag-Based Order Intelligence for Irish SMEs*

**用补助钱做什么（合格支出）**  
- 市场调研（爱尔兰 + 可选 UK）  
- 咨询（合规、会计口径、UX）  
- **原型/试点**：迁移试跑、推荐与 Tags 演示、打印/电话集成可行性验证  
- 自有研究工时（在规定上限内）

**不要写什么（易被拒）**  
- 把 **已完成的全站开发** 说成全新研发  
- **获批前** 已付的云服务费、工资  

### 8.2 Priming Grant（Feasibility 之后）

**课题标题（英文）**  
*Commercial Launch of LZFood — Mid-West Pilot Deployment, Customer Success, and B2B SaaS Sales*

**用补助钱做什么**  
- 招聘 **实施/客户成功 + 销售或开发**  
- 试点店培训与迁移实施  
- 营销（网站、本地餐饮活动）  
- 办公与固定 IT（遵守 LEO 对笔记本、手机等排除规则）

### 8.3 为何「先 Feasibility 再 Priming」更容易批

- 评审看到：**研究验证 → 再花钱雇人推广**，风险清晰。  
- 两阶段 **费用不重复**（同一份市场调研只报一次）。  
- 你们 **已有 MVP**，Feasibility 证明「下一阶段值得投」而非空想法。

## 九、竞争优势（简表，用于商业计划）

| 对比 | 大型国际 POS | 单店网页/二维码菜单 | **LZFood** |
